When I moved `pe-hackathon-2026` from Flask to FastAPI, the tempting version of
this migration was a full rewrite: new async framework, new async ORM, new
everything. That's also the version that turns a weekend project into a
month-long rabbit hole. This is the version I actually shipped &mdash; in
phases, with the existing Peewee data layer left alone.

## Why move off Flask at all

Flask isn't broken. The reasons to move were specific, not aesthetic:

- **Async support** for the endpoints that actually benefit from it (calls
  out to external APIs, anything I/O-bound that isn't touching the database)
- **Pydantic request/response models** instead of hand-rolled validation
- **Automatic OpenAPI docs**, which matters more than it sounds like once
  other people start hitting your API

None of that requires touching the database layer. That distinction is what
made the rest of the migration tractable.

## The ORM problem nobody warns you about

FastAPI is built around `async`/`await`. Peewee is not, and has no async
mode. The "correct" async-native answer is to swap in something like
SQLAlchemy's async engine or Tortoise ORM.

I didn't do that, on purpose. A data-layer rewrite is exactly the kind of
change that's hard to review, hard to roll back, and easy to get subtly
wrong in ways that don't show up until production. Swapping the web
framework and swapping the ORM are two different migrations wearing the
same trench coat &mdash; doing them at the same time just means that when
something breaks, you don't know which one broke it.

So Peewee stayed exactly as it was: synchronous, unchanged, still the
source of truth for every model.

## Running sync code inside an async framework

The fix is to stop pretending the sync calls are async, and instead push
them off the event loop explicitly:

```python title="app/db.py" showLineNumbers
from anyio import to_thread
from app.models import Recipe

async def get_recipe(recipe_id: int) -> Recipe | None:
    def _fetch() -> Recipe | None:
        return Recipe.get_or_none(Recipe.id == recipe_id)

    return await to_thread.run_sync(_fetch)
```

Every Peewee call gets wrapped the same way: a small sync function, handed
to a thread pool, awaited from the route. It's more boilerplate than a
native async ORM call, but it's boilerplate that's trivial to review and
doesn't change what the query actually does.

The one real gotcha: the thread pool has a finite size. If every request
does three sequential DB calls and traffic spikes, you can exhaust the pool
and start queueing requests behind each other for no reason other than
pool size. Worth sizing deliberately rather than trusting the default.

## Where Redis actually earned its place

Redis went in after the framework migration, not during it, and only where
it solved a real problem: read-heavy endpoints hitting the same rows
repeatedly (recipe lookups, mostly) were adding load to the database that
had nothing to do with actual write traffic.

The pattern is the standard cache-aside approach:

```python title="app/cache.py" showLineNumbers
import json
from redis.asyncio import Redis

redis = Redis.from_url("redis://localhost:6379/0")

async def get_cached_recipe(recipe_id: int):
    cached = await redis.get(f"recipe:{recipe_id}")
    if cached:
        return json.loads(cached)

    recipe = await get_recipe(recipe_id)
    if recipe:
        await redis.set(f"recipe:{recipe_id}", recipe.to_json(), ex=300)
    return recipe
```

Nothing exotic &mdash; check the cache, fall through to Peewee on a miss,
write back with a short TTL. The interesting part isn't the cache, it's
that it slots in above the existing `get_recipe` function without that
function needing to know Redis exists.

## Shipping it in phases

The whole thing landed as a sequence of small, individually-reviewable
changes rather than one migration PR: scaffold FastAPI alongside the
existing Flask app, move routes over one group at a time, wrap the Peewee
calls in the threadpool helper as each route moved, and only add Redis
once the framework migration was stable and boring. Each phase was
independently shippable and independently revertible, which is really the
whole point &mdash; the goal was never "migrate fast," it was "never have a
day where the app is broken and I can't tell which of the five things I
changed caused it."

## What I'd do differently

If I were starting over, I'd write the `to_thread` wrapper as a decorator
on day one instead of hand-wrapping the first half-dozen call sites and
refactoring later. Small thing, but it's the kind of small thing that's
obvious in hindsight and easy to miss when you're just trying to get the
first route working end to end.
